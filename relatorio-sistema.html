Sumário Executivo

Visão Geral da Avaliação

Desde o relatório de junho/2026, o maior risco identificado — persistência exclusiva em localStorage — deixou de existir. O sistema já roda sobre um backend real (Supabase: Postgres + Auth + Storage), com 22 tabelas, 39 políticas de RLS e write-through na maioria dos módulos críticos. Esta atualização foca no que mudou e, principalmente, no que ainda precisa de decisão urgente.

Diagnóstico Geral

A migração para Supabase avançou de forma consistente ao longo de ~25 commits: autenticação real com sessão e RLS, clientes, instalações, chamados, comunicados, notificações e documentos de cliente (agora em Storage, não mais base64) já sincronizam com o servidor. O ponto de maior atenção agora não é mais "o sistema tem backend?" — é garantir que as peças novas (convite de usuário via Edge Function, sincronização em tempo real, exclusão segura de usuário) estejam realmente ativas em produção e não apenas no código local.

Seção 01

O que já foi resolvido desde Junho/2026

Estes itens eram os riscos críticos do relatório anterior. Todos foram endereçados por commits reais no repositório — listados aqui para que a equipe saiba o que já não precisa mais de atenção.

🗄️

Backend real: Supabase (Postgres + Auth + Storage)

22 tabelas no banco (clients, profiles, installations, chamados, comunicados, notifications, tecnico_clients, client_documents, doc_checklists etc.) e 39 políticas de RLS. Deixou de existir o risco de perda total de dados ao limpar o navegador.

🔑

Autenticação real com sessão e RLS

Presidente, gestor, técnico, consultor, instalador e cliente autenticam de fato contra o Supabase Auth, com session restore e políticas de acesso por role. As credenciais deixaram de ficar só em texto puro no localStorage.

📄

Documentos de cliente em Supabase Storage

Antes eram base64 salvos no navegador (rápido de estourar o limite de 10MB). Hoje ficam no bucket client-documents, com URL assinada e toast visível (✅) confirmando o upload no servidor.

🔄

Telas de edição agora sincronizam de verdade

Edição de técnico, consultor, parceiro e cliente-portal escreviam só no localStorage e voltavam ao valor antigo no próximo login. As 4 telas agora chamam _sbRun(...profiles.upsert(...)), seguindo o mesmo padrão já usado na criação de usuários.

✉️

Convite de usuário sem expor chave de servidor no navegador

Criação de consultor/instalador/técnico/gestor passou a chamar uma Edge Function (invite-user) que roda no servidor com a service_role key, em vez de qualquer chamada administrativa direta do cliente. Ver ressalva na Seção 02, item 1 — a function ainda não está versionada no git.

🐛

Bug de seed de usuários órfãos — resolvido (2ª vez, causa raiz real)

confirmation_token nulo em auth.users gerava 500 no GoTrue e deixava usuários órfãos. Corrigido no seed.

📥

Exportação CSV já disponível

exportCSVClientes() e exportCSVLeads() já existem — o relatório de junho listava isso como lacuna; hoje é uma função ativa acessível pelo gestor.

Seção 02

Urgências para Avançar

Itens que precisam de decisão ou verificação imediata — não são melhorias de médio prazo, são riscos ativos ou funcionalidades possivelmente quebradas em produção agora.

🔴 Críticos

🔔

3 notificações nunca chegam ao usuário certo

Três dos pushes de notificação usam consultantId em vez de targetUserId como chave — a notificação é criada no banco mas nunca aparece na UI de ninguém. Bug conhecido e ainda não corrigido.

📡

Sem sincronização em tempo real entre usuários

O banco já é Postgres real via Supabase (que tem Realtime nativo via websocket), mas o app não assina nenhum channel() — dois usuários logados ao mesmo tempo (ex: gestor e consultor) não veem a alteração um do outro sem recarregar a página. É a lacuna mais cara do relatório de junho que ainda não foi endereçada, apesar do banco já suportar a solução sem custo adicional.

🟠 Altos

🗑️

Exclusão segura de usuário — adiada

Plano já está pronto (levantado em sessão anterior), mas a implementação foi adiada a pedido explícito. Continua não bloqueando o lançamento, mas sem isso não há caminho oficial de remover um usuário sem deixar registros órfãos no banco.

🔗

"Meu Link" do consultor está desativado

O formulário público de captação de leads foi desligado em 2026-07-20 porque enganava o visitante. O código foi mantido para retomar depois, mas não há decisão sobre quando ou como corrigir e reativar essa fonte de leads.

🔇

Fallback de autenticação é silencioso

Quando o Supabase rejeita ou fica indisponível, o login cai para autenticação local só com um console.warn('[AUTH FALLBACK]...'). Ninguém na equipe é alertado quando isso acontece — um problema de conectividade com o Supabase pode passar despercebido enquanto usuários operam sobre dados desincronizados.

🧹

Tabelas mortas no schema (Mural/Desafios)

mural_config, challenges e sales_feed continuam no banco mesmo após a feature de gamificação ter sido removida do app.js (~474 linhas removidas por ser feature isolada, sem impacto em comissão). Não quebra nada, mas é schema morto acumulando.

📏

app.js cresceu para 21.036 linhas

Aumentou desde o relatório anterior. Continua um único arquivo sem testes automatizados — qualquer erro de sintaxe quebra o sistema inteiro, e o risco de regressão silenciosa cresce a cada feature nova.

🟡 Housekeeping

✅

Edge Function invite-user confirmada ATIVA — mas não versionada no git

Verificado via supabase functions list --project-ref johywuxgohcwzkrzrjdq em 07/08/2026: a function está deployada e ACTIVE (versão 2, verify_jwt: true). Cadastro de usuário não está quebrado. O único gap real é que supabase/functions/invite-user/index.ts continua fora do controle de versão — se o código local divergir do deployado, ninguém vai notar até dar erro em produção.

📁

supabase/.temp/ fora do .gitignore

Metadados locais do Supabase CLI (project-ref, versões de serviço) aparecem como arquivo não rastreado e podem acabar indo pro repositório por engano num commit futuro.

Seção 04

Conclusão & Recomendações Finais

Síntese da avaliação e os 3 pontos de ação mais urgentes para a próxima semana.

Veredicto Geral O maior risco estrutural do sistema — persistência exclusiva em localStorage — já foi resolvido. O Portal do Vendedor agora roda sobre um backend real, com autenticação, dados e documentos sincronizados no Supabase. A Edge Function de convite de usuário foi verificada em produção e está ativa. O que resta não é mais "construir o backend", é fechar as pontas soltas dessa migração: corrigir as notificações que se perdem no caminho, ligar o Realtime que o banco já suporta, e versionar no git o que já está deployado.
